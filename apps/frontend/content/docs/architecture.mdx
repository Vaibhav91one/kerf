## Stack

pnpm workspaces, Node 22, TypeScript with no build step in the shared/CLI packages
(`allowImportingTsExtensions`), `node --test` instead of Jest/Vitest. Express + Prisma + Postgres on
the backend, Next.js on the frontend, Clerk for browser auth.

```
packages/shared   types, pure scoring logic, gamification, sanitisers — no I/O
apps/cli          the kerf CLI: login, sync, live, skills, projects
apps/backend      Express API + Postgres
apps/frontend     Next.js dashboard (this site)
```

The one line that matters most in that diagram: nothing crosses from "Your machine" into "API"
except a session's scores. The transcript itself — prompts, file contents, diffs — never leaves the
left box. See [Privacy model](/docs/privacy) for exactly what does cross.

## The extractor

`apps/cli`'s extractor is the actual product. It reads `~/.claude/projects` (Claude Code) and
`~/.codex/sessions` (Codex) JSONL transcripts, groups events into sessions, and derives a small set
of numbers per session — turn count, edit count, how many edits were rework, and the ratio between
them. Both agents' transcripts get normalised into one shared event shape before scoring runs, so
`packages/shared`'s scoring logic never needs to know which CLI produced a session.

## Live feed

`kerf live` heartbeats an in-progress session every 15 seconds. The backend keeps these as ephemeral
rows — no history, just "is this session still going" — and fans updates out over Server-Sent Events
to every connected dashboard tab. A tile goes dark automatically about a minute after the last
heartbeat, so there's no explicit "stop" event to miss.

## No event table, by design

There is deliberately no table storing raw events. The privacy model isn't "we could look but
choose not to" — there's no schema for it to land in even if something tried. What's stored is
already-aggregated numbers per session, described in [Privacy model](/docs/privacy).

## Deployment

Backend and frontend deploy as two services on Zerops from one `zerops.yml`. The backend is pinned
to a single container — several in-process stores (rate limiting, the SSE fan-out, the CLI-login
device-code map) assume exactly one, and a couple of those would fail outright rather than degrade
gracefully on a second replica. `/health` does a real database round-trip rather than just
confirming the process is alive, so the platform won't route traffic to a container whose migration
is still running or whose database is unreachable.
